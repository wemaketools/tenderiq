## How to use this glossary

- Terms are alphabetical within each section.
- "Where it appears" names the schema tables and columns (blueprint), screens (PRD screen IDs), business rules (BR) and acceptance scenarios (AC) where the term matters. Table names are the SQL names used throughout the [data model](03-data-model/README.md).
- State values are the exact codes stored in the database and mirrored in `src/contracts/enums.ts` ([ADR-0004](adr/0004-text-check-constraints-not-enums.md)). UI labels may be localized, but the meanings do not change (PRD §8.3).
- `DD-xx` cites an entry of the design decision log, `docs/plan/design-decisions.md`.
- Where a word has a business and a technical meaning (for example "contract"), see [Terms with more than one meaning](#terms-with-more-than-one-meaning).

## Procurement and business terms

| Term | Meaning | Where it appears |
|---|---|---|
| Abnormally low offer | An offer flagged for documented review under the applicable policy. It is never rejected automatically (PRD §9.3). | `commercial_evaluations.abnormally_low_flag`, `abnormally_low_review`; EVA-04 |
| Acknowledgment | A recipient's recorded confirmation of a notice, addendum, participation condition or tender version. It is distinct from delivery, from opening, and from acceptance of terms (BR-41). For submission readiness, `participant_acknowledgments` is authoritative. `notice_recipients.acknowledged_at` records the delivery-level event and is written in the same transaction when the acknowledgment comes from a notice (DD-42). | `participant_acknowledgments`, `notice_recipients.acknowledged_at`, `notifications.acknowledged_at`; permission `supplier.notices.acknowledge` (DD-23); COM-06, SUP-08 |
| Addendum | A formally approved and issued amendment to an issued tender. It records what changed, why, when, and whom it affects (PRD §3, FR-10). Any material change to scope, terms, submission or evaluation requires one (BR-16). It produces a new tender version and states what existing submissions must do: `none`, `acknowledge`, `supplement` or `replace`. An addendum that changes a deadline also updates `tenders.updated_at` in the same transaction, so it serializes against in-flight submissions (DD-15). | `addenda` (`materiality`, `existing_submission_action`, `resulting_version_no`), `addendum_lots`, `addendum_requirement_changes`; BUY-17; AC-10 |
| Advance notice | A published forecast of a planned procurement. It is not an invitation to bid (PUB-06). | `advance_notices`, `plan_items` |
| Affordability | Whether an offer fits the approved budget. It is shown separately from ranking (PRD §9.3). | `commercial_evaluations.affordability` (`within_budget`, `exceeds_budget`, `not_assessed`) |
| Alternative bid | A permitted variant offer, explicitly related to a primary bid (FR-12). | `bids.is_alternative`, `bids.alternative_of_bid_id`; `tenders.alternatives_allowed` |
| Alternative oversight | A documented compensating control, used when a small organization cannot separate duties. A control may not be silently disabled (PRD §5.4, BR-07). | `sod_policies.mode = 'alternative_oversight'`, `alternative_oversight_note`; `org_settings.sod_alternative_oversight_note` |
| Amount kinds | The distinct monetary measures that must never be presented interchangeably: estimate, approved budget, submitted price, evaluated cost, intended award, actual award, contract ceiling, committed spend and paid spend (PRD §3). Each has its own column and label (plan §3.7), and every money column has a currency column on the same row or on an explicitly named parent (DD-08). | For example `procurement_requests.estimated_value`, `tenders.budget_amount`, `commercial_evaluations.submitted_total`, `commercial_evaluations.evaluated_cost`, `lot_outcomes.awarded_value`, `contracts.ceiling`, `contract_invoices.amount` |
| Approval | A decision by an authorized person or committee against a specific version, amount, scope and evidence (PRD §3). A material change invalidates it (BR-10, AC-06). Deciding a step requires `approval.decide`, the decision-specific permission (for example `award.approve`) and sufficient authority (DD-24). | `approval_requests` (`subject_type`, `subject_version`, `content_hash`, `amount`, `currency`, `status`), `approval_steps`; COM-04, COM-05 |
| Arithmetic correction | An authorized correction of a supplier's arithmetic. It is recorded separately from the submitted figures, together with the correction rule, the approval and any supplier acknowledgment (PRD §9.3, BR-29). | `commercial_evaluations.arithmetic_correction`, `correction_rule`, `correction_approved_by`, `supplier_ack_at` |
| Authority limit | The maximum value and scope that a user, role or committee may approve for a decision type (BR-06). Cross-currency authority converts with `exchange_rates` at the request date. With no rate, the step routes to the next level up, never to an assumed pass (DD-24). | `authority_limits` (`decision_type`, `max_amount`, `currency`, `legal_entity_id`, `category_id`); `exchange_rates`; ADM-05; AC-05 |
| Award | The approved allocation of all or part of a procurement to one or more suppliers. A preferred-bidder decision is not an award (PRD §3, BR-31). Each lot has an explicit outcome (BR-33). A tender can have several award recommendations over time, each covering the lots listed in its lot outcomes, so lots on different timelines are supported (DD-14). | `award_recommendations`; `lot_outcomes.outcome` (`award`, `partial_award`, `conditional_award`, `no_award`, `cancelled`); BUY-26; AC-26 |
| BAFO (best and final offer) | A formally requested final response round. It has an eligible audience, consistent instructions, permitted changes, a deadline, a receipt, opening rules and a declared evaluation treatment. Earlier offers stay visible for comparison (FR-16). It requires explicit procedural authority (BR-30). | `final_offer_rounds` (`procedural_authority_ref` not null), `final_offer_invitees`, `bids.round_type = 'bafo'`; BUY-27, SUP-19; AC-23 |
| Bid (response) | A supplier's offer for an event or one or more lots: answers, commercial terms, declarations and evidence (PRD §3). One container exists per supplier, tender and bidding combination, enforced by a `UNIQUE NULLS NOT DISTINCT` key on (`tender_id`, `supplier_tenant_id`, `is_alternative`, `round_type`, `final_offer_round_id`) (DD-02). | `bids` (`submission_state`, `compliance_status`, `evaluation_status`, `round_type`), `bid_lots` |
| Bid revision | A distinguishable edition of a response. Submitted revisions and their receipts remain on record even after a later revision becomes effective (PRD §3). States: `draft`, `internal_review`, `approved_internally`, `submitted`, `superseded`, `withdrawn`, `late_rejected`, `submission_failed`. | `bid_revisions`; SUP-15 to SUP-17 |
| Bid validity | The period for which a supplier's offer remains open for acceptance. | `tenders.bid_validity_days`, `bid_commercial_terms.validity_days`; `bid_declarations.declaration_type = 'bid_validity'` |
| Bid/no-bid decision | A supplier's decision whether to pursue an opportunity. The pursuit decision and its internal rationale are private to the supplier. The buyer-visible bid intent and shared decline reason change only through the explicit "notify buyer" action on SUP-07 or SUP-09 (DD-41). | Private: `pursuits.decision`, `internal_rationale`. Shared: `participants.bid_intent`, `shared_no_bid_reason` |
| Blocking complaint | A complaint that places a hold on the award or contracting actions specified by policy (BR-32, AC-25). | `complaints.is_blocking`, `complaints.hold_id`; `holds.hold_type = 'complaint_hold'` |
| Briefing, site visit | A session for participants, with registration, capacity, attendance, accessibility needs and minutes. Mandatory attendance is declared in advance (FR-10). | `sessions` (`session_type` `briefing` or `site_visit`), `session_registrations`; BUY-18, SUP-11 |
| Buyer (buyer organization) | The organization that runs procurements. It is the primary boundary for its policies, users, confidential records, supplier assessments and reporting (PRD §2.1). | `tenants.kind = 'buyer'`; [ADR-0001](adr/0001-tenancy-equals-organization.md) |
| Buyer-supplier relationship | A buyer's own record of a supplier: status, owner, risk rating, restrictions, contacts. It is not visible to other buyers (BR-45), and it is buyer-internal: tagged [R], so the supplier cannot reach it either (DD-03). | `buyer_supplier_relationships`, `relationship_contacts`; BUY-32 |
| Capacity | The role in which a person is acting for an organization at a given moment, for example "Evaluator" at a buyer or "Contributor" at a supplier. The current organization and capacity are confirmed before any consequential action (PRD §2.1, BR-02, COM-02). | `memberships.title`; `audit_log.actor_capacity`; `/select-organization`; AC-02 |
| Clarification (bid) | A formal question to a supplier about its submitted response, with a recorded permitted scope, deadline, response and effect. It cannot become an improved offer (BR-22). | `bid_clarifications` (`source`, `permitted_scope`, `effect`); EVA-03, SUP-18 |
| Clarification (tender) | A supplier question about tender requirements and the buyer's answer, published to a recorded audience. Shared answers normally omit the questioner's identity (FR-10). Public clarification URLs carry the buyer slug (DD-22). | `questions` (`audience`, `sanitized_question`, `status`, `after_deadline`); BUY-16, SUP-10, PUB-04; `/clarifications/:buyerSlug/:ref` |
| Closing | The end of ordinary submissions at the official deadline. The tender moves to `closed` ("closed / awaiting opening"), and sealed content stays protected (PRD §8.2). | `tenders.status = 'closed'`, `tenders.closed_at`; `close-tenders` job; BUY-19 |
| Committee, quorum | A standing group with a purpose (evaluation, award, opening, complaints, policy, other) and a minimum attendance for valid decisions. | `committees` (`quorum`), `committee_members`; `policy_profile_versions.opening_quorum`; `opening_sessions.quorum_required` |
| Complaint (challenge) | A formal objection with a complainant, grounds, dates, evidence, an independent owner, a decision, and an effect on the procurement (PRD §3). | `complaints` (reference `CMP-2026-0001`), `complaint_events`; BUY-29, SUP-22; AC-25 |
| Compliance check | An assessment of a submitted bid for timeliness, declarations, required documents, eligibility, mandatory requirements, attendance, acknowledgments, securities, lot restrictions and qualification status. Each finding cites evidence and has a disposition (FR-13). Compliance checks are buyer-internal ([R], DD-03). | `compliance_checks` (`finding_class` `administrative_omission`, `substantive_noncompliance`, `clarifiable` or `none`; `result`); BUY-21; AC-17 |
| Conflict declaration | A person's declaration of financial interest, personal relationship, prior employment, bid-preparation involvement or other conflict, with a reviewed disposition. It is required before access to restricted assessment material (BR-08). A declaration with `has_conflict = true` blocks restricted access while `pending_review`. Access resumes only on `cleared` or `mitigated`, and `recused` or `reassigned` block access permanently for that subject (DD-25). | `conflict_declarations` (`has_conflict`; `disposition` `pending_review`, `cleared`, `mitigated`, `recused` or `reassigned`); EVA-01 |
| Confidentiality undertaking | A signed acceptance of confidentiality terms for a subject. It is required before restricted access (BR-08) and can be a participation condition. | `confidentiality_undertakings`; `participants.confidentiality_accepted_at`; `participation_conditions.condition_type` |
| Consortium (joint venture) | A bidding group with named members, a lead party, agreed responsibilities and evidence of authority (PRD §3). | `bids.is_consortium`, `lead_member_name`; `consortium_members` |
| Contract | The binding commercial arrangement: parties, scope, values, dates, documents, obligations and change history (PRD §3). States: `draft`, `under_review`, `awaiting_signature`, `signed_not_effective`, `active`, `suspended`, `expired`, `terminated`, `closed`. The daily `contract-dates` job moves `signed_not_effective` to `active` when the effective date is reached, and `active` to `expired` after `term_end` while open obligations remain (DD-19). See also "API contract". | `contracts` (reference `C-2026-0001`), `contract_lot_allocations`, `contract_signatories`; CON-01 to CON-11 |
| Contracting entity | The legal entity of the buyer that becomes party to a contract. It must be identified before a binding commitment is authorized (BR-04). | `legal_entities.is_contracting_entity`; `contracts.legal_entity_id` (not null) |
| Debrief | An explanation given to an unsuccessful supplier of its own result, without other bidders' confidential content (FR-17, AC-27). | `debrief_requests`; SUP-21, BUY-29 |
| Delegation | A temporary grant of approval authority for specified decision types, value, entity, category and dates. A delegate cannot exceed the delegator's own limit (PRD §5.3, BR-06). Request-time checks compare its dates directly, and the `expire-access` job only updates display statuses and sends notices (DD-18). | `delegations`; `approval_steps.acting_for_user_id`, `delegation_id`; `audit_log.delegation_id`; ADM-05 |
| Due diligence | Verification of the claims relevant to a proposed award, such as financial position, capacity, insurance and restrictions. Each finding has a disposition and an owner (FR-16). | `due_diligence_cases`, `due_diligence_findings` (`is_award_blocking`); BUY-25; AC-24 |
| Effective revision | The bid revision that currently counts: by default the last successfully submitted, non-withdrawn revision before closing (PRD §17.2). A failed replacement does not supersede it. An explicit withdrawal removes it (BR-19). | `bids.effective_revision_id` (null until a successful receipt; a deferrable foreign key, DD-01); partial unique index allowing one `submitted` revision per bid; SUP-17; AC-12 |
| Envelope | A business separation of response material, opened at different permitted stages (PRD §3). Values: `qualification`, `technical`, `commercial`. Every envelope column has this CHECK. The envelope of each sealed table is fixed: answers take the requirement's envelope, answer documents follow their answer, declarations are `qualification`, subcontractors and key personnel are `technical`, and prices, commercial terms and exceptions are `commercial` (DD-05). See also "Two-step upload envelope". | `tender_envelopes` (`open_order`), `requirements.envelope`, `bid_answers.envelope`, `receipt_inventory_items.envelope`, `evaluation_criteria.envelope`, `opening_sessions.envelope`, `envelope_openings` |
| Envelope opening (unseal record) | The record that a specific envelope of a specific bid revision has been opened. It is the first of the four conditions for reading sealed content (plan §3.3). A single-stage opening (`opening_sessions.envelope = 'all'`) writes one row per envelope in the same transaction (DD-05). It is buyer-internal ([R], DD-03). | `envelope_openings` (`unique (revision_id, envelope)`); [ADR-0003](adr/0003-application-layer-sealing.md) |
| Evaluated cost | The cost used for commercial comparison. It is derived from the submitted total after authorized arithmetic corrections, currency conversion and the issued comparison basis (taxes, quantities, options, discounts, whole-life costs). It is distinct from the submitted price (PRD §3, §7.11, §9.2). In the PRD §9.2 example it is 100,000 vs 120,000. | `commercial_evaluations.evaluated_cost` vs `submitted_total`; EVA-04; AC-19 |
| Evaluation | An assessor's documented assessment of an eligible response against the approved criteria (PRD §3). A missing score is never treated as zero (AC-18). | `evaluation_scores` (`score` null until scored), `score_corrections`; EVA-02 |
| Evaluation assignment | The allocation of an evaluator to a tender or lot, bids and criteria, with a due date and declarations. Assignment, not administration, grants access (BR-26). States: `not_started`, `in_progress`, `submitted`, `returned`, `finalized`, `recused`, `reassigned`. | `evaluation_assignments`; EVA-01 |
| Evaluation criterion | A declared basis for assessment with weight (maximum points), scale, guidance, threshold and envelope (PRD §3). | `evaluation_criteria` (`max_points` numeric(12,6), `is_price`, `min_score`, `envelope`), `scale_anchors` |
| Evaluation plan | The approved method: scale, aggregation (moderation) method, price method and weight, thresholds, decimal places for calculation and display, comparison currency and FX basis (PRD §9.1). | `evaluation_plans`, `tie_break_rules`; BUY-11 |
| Evaluation result | The computed non-price, price and total score for a bid, with gate pass or fail, rank and any tie-break applied. | `evaluation_results` (`total_score`, `total_score_display`, `rank`, `status`); EVA-06 |
| Event type | The kind of sourcing event: `rfi`, `rfq`, `rfp` or `tender`. | `tenders.event_type`, `procurement_strategies.event_type` |
| Evidence item | A supplier-owned substantiation such as a registration, financial statement, certificate, insurance, license or reference, with issuer, period, expiry and verification status (PRD §3). The `evidence-expiry` job only flags and notifies. `status = 'expired'` is set by the suppliers domain when the supplier views or renews the item, or by the suppliers-owned helper the job calls (DD-20). | `evidence_items` (supplier tenant), `evidence_shares`; SUP-05 |
| Evidence submission | An immutable record of which edition of an evidence item was used in a buyer process. Withdrawing future sharing does not erase it (FR-02, BR-25). Bids, selection, contracts and qualification append these snapshots through the suppliers-owned helper `snapshotEvidence()` (DD-17). | `evidence_submissions` (buyer tenant, `context_type`), `qualification_answer_evidence` |
| Exclusion | A decision to remove a bid from the competition, with grounds, approval, notification and a challenge route. Excluded bids stay on record but are not ranked (FR-13). | `exclusions`; `bids.compliance_status = 'excluded'`; BUY-21 |
| Fairness review | A review triggered when a supplier was involved in shaping a strategy or specification (PRD §7.2). | `fairness_reviews`; `market_research_entries.prior_specification_involvement` |
| Final award | The formal award after all approvals, satisfied conditions, resolved blocking complaints and completed waiting periods (FR-17). It is distinct from intent to award, and it is its own approval per lot outcome, with approval subject type `final_award` (DD-14). | `lot_outcomes.status = 'final_awarded'`, `final_awarded_at`, `final_award_approval_id`; `approval_requests.subject_type = 'final_award'`; `notices.notice_type = 'final_award'` |
| Formal notice | An approved, versioned communication with a defined audience, issue time and, where applicable, required acknowledgment (PRD §14.2). Delivered on both channels: in-app, and by email where email is enabled, with the email limited to the title, the official deadline and a link (DD-44, [ADR-0007](adr/0007-in-app-formal-notices.md)). Opening, acknowledgment and terms acceptance happen in the product. | Handover | The package passed from procurement to the named contract manager: final scope, commitments, exceptions, measures, risks and contacts. | Hold | A separate condition on a tender, lot, contract, application or record, with an owner, reason, scope, start, review date and release. | Obligation, milestone, deliverable | A contractual commitment or dated outcome with an accountable party, evidence of completion, acceptance criteria and a consequence (PRD §3). | `obligations.kind`, `obligation_evidence`, `acceptance_decisions`; CON-05, CON-06; AC-30 |
| Official deadline | The deadline expressed as date, time, named time zone and offset. Displaying a local conversion must not obscure it (BR-11). | Official time zone | The IANA time zone that governs an event's dates. `tenants` holds the organization's authoritative default (DD-10). | `tenders.official_time_zone` (not null), `tenants.official_time_zone`, `calendars.time_zone` |
| Opening session | The recorded event at which eligible envelopes are opened, with the required officer, witnesses or quorum, time, irregularities and minutes (FR-13). | `opening_sessions`, `opening_participants`; BUY-20; AC-15 |
| Participant | A supplier's participation record for a tender: source, invitation, access decision, confidentiality acceptance, bid intent and qualification gate (PRD §3 "participation record"). | `participants`, `participant_lot_selections`, `participant_acknowledgments`, `document_access_log`; BUY-15, SUP-07, SUP-08 |
| Participation condition | A condition a supplier must meet for document access or participation, such as a confidentiality undertaking, a required qualification, a mandatory briefing, registration or eligibility review. | `participation_conditions` (`blocking`) |

| Preferred bidder | A conditional selection outcome that identifies scope, value, rationale, remaining checks, negotiation topics and a fallback. It is not an award (FR-16, BR-31). | `preferred_bidders` (`fallback_bid_id`, `status`); BUY-24; AC-24 |

## Terms with more than one meaning

| Word | Business meaning | Technical meaning |
|---|---|---|
| Contract | A commercial agreement between a buyer and a supplier (`contracts`, CON screens). | An API contract in `src/contracts` that defines an endpoint's shape. Documents say "API contract" whenever the context is ambiguous. |
| Envelope | A sealed separation of bid material: qualification, technical, commercial. | The two-step upload envelope for files (brief §5.9). |
| Session | A briefing or site visit (`sessions`), opening session (`opening_sessions`), moderation session (`moderation_sessions`) or assessment session (`assessment_sessions`). | An authentication session held by supabase-js in the browser. The database connection never carries session state (brief §5.6). |
| Notice / notification | A notice is a formal, versioned communication (`notices`). | A notification is a per-user in-app item (`notifications`), which may point to a notice or be a task, reminder, system or promotional message. |
| Suspension | A hold type (`holds.hold_type = 'suspension'`), or contract status `suspended`. | Tenant status `suspended`, membership status `suspended`, user status `suspended`, or an access restriction of type `suspension`. |
| Exception | A late submission exception (`late_submission_exceptions`), a delivery exception task (`tasks.task_type = 'delivery_exception'`), or an integration exception (`integration_exceptions`). | A thrown error. Exceptions are reserved for unexpected failures, and expected ones use `Result` (brief §5.3). |
| Assignment | An evaluation assignment (`evaluation_assignments`) or a tender team membership (`tender_team_members`). | A role assignment (`role_assignments`) granting permissions within a scope. |
| Template | A content template in the library (`templates`: tender package, questionnaire, criteria set, clause, letter, checklist, contract). | A role template (`role_templates`) copied into each tenant, or a notification rule template (`notification_rules.subject_template`). |
| Register | A list screen such as the request register (BUY-02), tender register (BUY-07) or contract register (CON-01). | A registry file written by the Integration step ([ADR-0009](adr/0009-registries-wired-by-integration.md)). |
| Clarification | A tender question and answer (`questions`). | A post-closing bid clarification (`bid_clarifications`). Both are business terms, but they are different records with different rules (BR-22). |
| Invitation | A tender invitation to a supplier organization (`participants.invitation_status`, SUP-07). | A user invitation to join an organization (`invitations`, `/invite/:token`), accepted through `POST /api/v1/me/invitations/:token/accept` (DD-27). |
| Idempotency key | Not a business term. | Either a queue or job dedupe key in `job_idempotency_key` (brief §9.5, DD-19), or the HTTP `Idempotency-Key` request header stored in `request_idempotency` (DD-39). |
