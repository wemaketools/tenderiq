# TenderIQ — Design Decision Log (resolutions of documentation review open points)

Status: APPROVED with the architecture plan on 2026-09-29 (DD-43 … DD-45 record the owner decisions of 2026-09-29). These resolve the structural open points raised while writing `docs/technical`. They are **binding for both stages**, and where they differ from `schema-blueprint.md` or `architecture-plan.md`, this log wins (those files were amended to match). The remaining open points are either owner decisions (§E) or implementation details that are legitimately settled by the Stage A contracts or Stage B migrations (indexed in `docs/technical/README.md` §6).

## A. Schema structure

| ID | Topic | Decision |
|---|---|---|
| DD-01 | Forward foreign keys | A column that references a table created in a **later** migration stays a plain `bigint` in its own migration. The migration that creates the target table adds the FK with `ALTER TABLE … ADD CONSTRAINT`. This covers `audit_log.delegation_id`, `audit_log.support_grant_id`, `notices.tender_id`, `holds.complaint_id`, `procurement_requests.replaces_contract_id`, `procurement_requests.routed_contract_id`, `plan_items.tender_id`, `tender_versions.addendum_id`, `participation_conditions.session_id`, `bids.final_offer_round_id` and `templates.source_tender_id`. Same-migration cycles are added at the end of the migration as `DEFERRABLE INITIALLY DEFERRED`: `bids.effective_revision_id → bid_revisions`, `bid_revisions.receipt_id → submission_receipts`, `documents.current_version_id → document_versions`, `policy_profiles.current_version_id`, `templates.current_version_id` and `qualification_programs.current_version_id`. `audit_log` is partitioned, so FKs *from* it are not created (ids only). |
| DD-02 | Nullable columns in unique keys | Every unique constraint that includes a nullable column uses `UNIQUE NULLS NOT DISTINCT` (PG 15+). Examples: `tender_milestones (tender_id, lot_id, milestone)`, `price_gate_releases (tender_id, lot_id)`, `notice_recipients (notice_id, supplier_tenant_id, recipient_user_id)`, and `bids (tender_id, supplier_tenant_id, is_alternative, round_type, final_offer_round_id)`. The last one replaces the `coalesce` expression. |
| DD-03 | Supplier-scope tags | `[S]` now means **supplier-accessible**. Such a table is on the explicit allow-list `supplier-scoped-tables.ts` that `forSupplier` uses. A new tag **`[R]`** means the table carries `supplier_tenant_id` for **reference only** (buyer-internal) and is **not** reachable by `forSupplier`. The allow-list is generated from the blueprint tags, not from column presence. `[R]` tables: `buyer_supplier_relationships`, `relationship_contacts`, `reassessment_triggers`, `integrity_screenings`, `envelope_openings`, `compliance_checks`, `exclusions`, `evaluation_scores`, `moderated_scores`, `commercial_evaluations`, `evaluation_results`, `assessment_findings`, `reference_checks`, `shortlist_entries`, `preferred_bidders`, `due_diligence_cases`, `due_diligence_findings`, `negotiations`, `late_submission_exceptions`, `renewal_options`. Suppliers learn outcomes only through notices and the supplier-facing projections defined in the contracts. `qualification_answer_evidence` becomes `[S]`. A guard test asserts that no `[R]` table is on the allow-list. |
| DD-04 | `[G]` tables that name a customer | `subscriptions.tenant_id`, `offboarding_plans.tenant_id` and `service_incident_impacts.tenant_id` are renamed to **`customer_tenant_id`**, so the tenant-scoped generator never picks them up. |
| DD-05 | Sealed envelope mapping | `bid_answers.envelope` is copied from the requirement. `bid_answer_documents` follows its parent answer. `bid_declarations` is `qualification`. `bid_subcontractors` and `bid_key_personnel` are `technical`. `bid_prices`, `bid_commercial_terms` and `bid_exceptions` are `commercial`. `receipt_inventory_items.envelope` records the envelope of each file. Every envelope column has CHECK (`qualification`, `technical`, `commercial`). A single-stage opening (`opening_sessions.envelope = 'all'`) writes one `envelope_openings` row **per envelope** in the same transaction. |
| DD-06 | Missing CHECK lists / types | `tenders.award_model` CHECK (single, per_lot, multiple). `evaluation_criteria.envelope` CHECK (technical, commercial, qualification). `requirements.evidence_required` is `text` (null = none). `job_run.status` CHECK (running, succeeded, failed). The brief wins: unimplemented jobs write `failed` + 501, and `not_implemented` is removed. `invitations.role_ids bigint[]` holds **tenant role ids**. |
| DD-07 | Missing uniqueness | Unique keys: `qualification_program_versions (program_id, version_no)`; `participant_lot_selections (participant_id, lot_id)`; `addendum_lots (addendum_id, lot_id)`; `session_registrations (session_id, supplier_tenant_id) WHERE status <> 'cancelled'`; `scale_anchors (plan_id, value)`; `tie_break_rules (plan_id, sequence)`; `release_checks (tender_id, check_area, draft_revision)`; `publications (tender_id, version_no, channel)`; `change_requests (contract_id, number)`. |
| DD-08 | Currency on amounts | Add `scope_currency` to `qualification_applications` and `qualification_decisions`, and `currency` to `change_requests`. Every money column has a currency column on the same row or on an explicitly named parent. |
| DD-09 | Reference numbers | The year segment is the year **in the tenant's official time zone**. Add prefixes `PP-` (procurement_projects) and `QA-` (qualification_applications). `change_requests.number` is an `integer` sequence per contract (`max + 1` under a `SELECT … FOR UPDATE` lock on the contract row) and is displayed as `CR-0001`; it does not use `next_reference`. |
| DD-10 | Identity defaults | `tenants` is authoritative for `official_time_zone`, `working_languages` and `default_currency`. `org_settings` keeps only procurement configuration. `org_settings.currencies` is renamed `accepted_currencies`, and its `official_time_zone` and `working_languages` columns are dropped. |
| DD-11 | Partition tenant of cross-tenant rows | `audit_log`: the tenant that **owns the affected record**. A supplier submitting a bid on a buyer-owned row is audited in the buyer's partition, with `actor_capacity` naming the supplier org. `[G]` records go to the operator tenant. Support-access events are written to the **customer** tenant, so the customer can review them. `notifications`: the **recipient's** tenant for that notice (the supplier tenant for supplier recipients). |
| DD-12 | Storage keys | `<owning-record tenant_id>/<related_type>/<related_id>/<document_id>/<version_no>-<sanitized name>`. The buyer tenant owns procurement records even for supplier uploads. `documents.owner_tenant_id` records who uploaded. |
| DD-13 | Views | `v_bid_receipt_metadata` exposes `tenant_id` (for forTenant), `supplier_tenant_id`, the supplier legal name **valid at received_at** (from `supplier_legal_names`), bid, effective receipt no, received_at, status (including withdrawn, never drafts) and document_count. `v_public_tenders`: `participation = 'open'`, the buyer's `portal_settings`/`org_settings.public_portal_enabled` is on, and status ∈ {open, closed, under_assessment, award_pending, awarded, partially_awarded, completed_without_award, information_collected, cancelled}. `v_public_awards`: only `public_award_notices.status = 'published'`. `v_qualification_status`: the latest non-superseded decision per (tenant, supplier, program), ordered by `effective_from desc, id desc`, with scope, dates, conditions and `effective_status`. `not_assessed` rows come from active relationships × active programs. |
| DD-14 | Approval subject types | Add `obligation_waiver`, `security_release`, `dispute_decision`, `contract_difference` and `final_award`. `contracts.difference_approval_id` uses `contract_difference`. `contract_disputes.authorized_decision_id` references `approval_requests`. Final award (distinct from intent) is its own approval per lot outcome (`lot_outcomes.final_award_approval_id`). A tender can have several `award_recommendations` over time, each covering the lots listed in its `lot_outcomes`, so lots on different timelines are supported. |
| DD-15 | Deadline authority | `lots.submission_deadline`, when set, is authoritative for that lot. Otherwise the tender's `tender_milestones(submission_deadline, lot_id null)` applies. Issuing an addendum that changes a deadline also updates `tenders.updated_at` in the same transaction, so the submission path's `FOR SHARE` lock on the tender row serializes against deadline changes. `tenders.scheduled_release_at` is authoritative for scheduling. `publications.scheduled_at` mirrors it per channel. |

## B. Ownership, services and jobs

| ID | Topic | Decision |
|---|---|---|
| DD-16 | Unowned tables | `tasks` → approvals service. `comments`, `holds`, `record_snapshots` and `process_decisions` → core service (lifecycle), which exposes `recordProcessDecision()`. `exchange_rates` → evaluation domain. `price_gate_releases` → evaluation (written by the chair, permission `evaluation.chair`). `category_catalog` → baseline `seed.sql`. `exports` + the `exports` queue handler → documents service `requestExport()`, with per-type generators registered by domains in `documents/export-registry.ts` (wired by Integration). |
| DD-17 | Additional allowed cross-domain writes | suppliers → `tenants` (buyer-created provisional supplier). bids, selection, contracts and qualification → `evidence_submissions` (append-only snapshots through the suppliers-owned helper `snapshotEvidence()`). opening → `submission_receipts.status = 'selected_for_evaluation'`. contracts → `integration_exceptions` (external signature failure, AC-33). |
| DD-18 | Grant expiry | The request-time checks always compare `starts_at`, `expires_at` and `revoked_at` directly. Expiry jobs only update display statuses and send notices. The single `expire-grants` job is split into jobs owned by each table's owner: `expire-access` (org-admin: grants, restrictions, delegations, invitations), `expire-approvals` (approvals) and `expire-support-access` (operations). |
| DD-19 | Added jobs | `contract-dates` (daily 02:50): `signed_not_effective` → `active` when the effective date is reached; `active` → `expired` after `term_end` (open obligations remain); securities `expiring`/`expired`. `report-schedules` (hourly :05): runs due report definitions and re-checks each recipient's authorization at issue time. `notification-digests` (daily 05:00): digest preferences. `notice-reconciliation` (every 10 min): re-enqueues `notice_recipients` still `pending` after 10 minutes (brief §9.5 safety net). Alerts are deduplicated by an idempotency key `<job>:<entity>:<window>` in `job_idempotency_key`. |
| DD-20 | Expiry semantics | `qualification-expiry` does **not** write decisions. `v_qualification_status` derives `expired`, and the job creates tasks and notices. `evidence-expiry` only flags and notifies; `evidence_items.status = 'expired'` is set by the suppliers domain when the supplier views or renews the item, or by the suppliers-owned helper the job calls. `retention-eligibility` writes `disposal_requests` rows in `proposed` or `blocked` status. |

## C. API and security

| ID | Topic | Decision |
|---|---|---|
| DD-21 | `/me` personal inbox | `/api/v1/me/tasks`, `/me/notifications`, `/me/approvals/:id`, `/me/documents/:id` and `/me/search` return **the caller's own rows across all active memberships**, each labelled with its organization. Actions on a row require `X-Tenant-Id` equal to the row's tenant. Global search still filters every result by the caller's authorization **in the row's tenant**. |
| DD-22 | Public and supplier references | References are unique per buyer, so public and supplier URLs carry the buyer slug: `/opportunities/:buyerSlug/:ref`, `/awards/:buyerSlug/:ref`, `/clarifications/:buyerSlug/:ref`. Supplier API paths use tender ids. |
| DD-23 | Permission catalog additions | `org.support_access.authorize` (buyer admin authorizes an operator support grant), `supplier.notices.acknowledge`, `dashboard.view` (buyer BUY-01), `supplier.dashboard.view` (SUP-01). Price-gate release uses `evaluation.chair`. |
| DD-24 | Approver permissions | Deciding a step requires `approval.decide` **and** the decision-specific permission (e.g. `award.approve`) **and** sufficient authority. Cross-currency authority uses `exchange_rates` at the request date. With no rate, the step routes to the next level up (never an assumed pass). |
| DD-25 | Conflict gating | A declaration with `has_conflict = true` blocks restricted access while its disposition is `pending_review`. Access resumes only on `cleared` or `mitigated`. `recused`/`reassigned` block permanently for that subject. |
| DD-26 | Role scope matching | A role assignment scoped to a legal entity, department, category (including descendants) or project covers a tender when the tender's corresponding column matches. Lots inherit from their tender. Contracts inherit through their tender and also match on their own legal entity. |
| DD-27 | Invitation acceptance | `POST /api/v1/me/invitations/:token/accept` is the one route the auth middleware allows for users in status `invited`. Accepting activates the membership, and the user if needed. Supplier registration creates tenant (status `pending`), user (`invited`), a pending membership and the supplier profile in one transaction and **commits**. **After the commit**, it calls the Auth Admin invite, because brief §5.6 forbids network calls inside transactions. If the invite fails, a short follow-up transaction sets the registrant’s `invitations` row (tenant = the new supplier tenant) to `send_failed`. The state guard allows a retry, and a successful resend sets it back to `pending`. The user sees "we could not send the verification email — try again". A "resend verification" action handles retries, and the unique `users.email` constraint rejects a second registration with the same email. Abandoned pending registrations stay visible to operators in the supplier registration and duplicate review, where they can be closed. |
| DD-28 | Public write endpoints (abuse) | Add table `rate_limit_buckets [G]` (`key_hash`, `window_start`, `count`, PK key_hash + window_start) and an app middleware that limits public POSTs (registration, register interest, access requests) per IP hash and per email hash. There is no external service. |
| DD-29 | Sign-in assurance | MFA and step-up (PRD FR-03 "may be required as business policy") are **not** in the initial release; the brief disables MFA. They are recorded as a later extension using Supabase MFA. |
| DD-30 | SPA document headers | A CSP `<meta http-equiv>` in `index.html` (self + Supabase URL for auth; fonts self-hosted). The Hono app sets API headers. There are still no header rules in `vercel.json`. |
| DD-31 | Audit content for sealed records | `before_state`/`after_state` never contain sealed content or evaluator scores. Those actions record ids and hashes only, with `sensitivity = 'restricted'`. The audit viewer shows restricted rows only to `audit.view` holders, redacted to metadata. |

## D2. Owner decisions recorded as design decisions (2026-09-29)

### DD-43 — Real authentication from Stage A

The local Supabase CLI stack runs in Docker from Stage A, and Stage A uses Supabase **Auth** only (no application schema yet).
- `npm run auth:personas` creates or updates every demo persona in local Supabase Auth through the Admin API. It is idempotent and local-only, and uses the password `test1234`.
- The SPA uses supabase-js exactly as in production. The mock API verifies the Supabase JWT with the real `src/server/lib/auth/verify.ts` (brief §5.7 checks, using the real `lib/config` and `lib/supabase` written in Stage A) and maps the verified email to its fixture persona. Unknown accounts get 401.
- In local development builds only (`import.meta.env.DEV`), the sign-in page lists demo accounts for one-click sign-in. Production builds exclude it, and `scan-bundle` checks this.
- The prototype banner appears when `/api/v1/me/context` reports `environment.mode = 'prototype'`.
- Password-reset emails from Supabase Auth are visible in Mailpit (`http://127.0.0.1:54324`) from Stage A. Invite and registration emails follow in Stage B, when the real API calls the Auth Admin invite.

### DD-44 — Email channel

`DeliveryChannel` has `in_app` and `email` implementations. `email` uses **nodemailer over SMTP**; nodemailer is the one approved added runtime dependency.
- Locally, SMTP goes to **Mailpit**: `supabase/config.toml` `[inbucket] smtp_port = 54325`, and a message is marked `delivered` when Mailpit accepts it.
- Config: `EMAIL_ENABLED`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`. Where email is not enabled, no email delivery rows are written.
- Formal notices go to both channels. Non-mandatory events follow user preferences.
- Email content is limited to title, official deadline and a link. There is never bid, evaluation or other confidential content (BR-43, ADM-12).
- The hosted provider (and its delivery-event webhooks) is **deferred**; see `email-delivery-options.md`. The same SMTP credentials will serve Supabase Auth in hosted environments.

### DD-45 — Node 24

Node **24** everywhere: `engines` `24.x`, `.nvmrc` `24`, CI `node-version: 24`, and Vercel Node.js 24.x via `engines`. This deviates from the brief's Node 22 pin, because Node 22 reaches end-of-life on 2027-04-30.

### DD-46 — Action placement: section actions in the top bar, page actions in the content area (2026-09-30)

Owner decision during the prototype review. It amends architecture-plan §7 ("one primary action in the top bar").
- **The top bar never moves.** Search, tasks, notifications and help are always the last items of the top bar, in the same place on every page. Pages do not put buttons in the top bar.
- **Section action.** A sidebar destination may define one action that applies to the whole destination, usually "New …" (for example "New request" for Requests). The top bar shows it in accent teal, to the **left of the search box**, on **every** page of the destination, including the pages the user drills into, and hides it only on the page it leads to. It is declared on the nav item (`NavItem.sectionAction`: label, target, icon, permission). It always navigates. Where a destination creates through a dialog, the target is its list page with `?new=1`, and the page opens the dialog while the parameter is present (`useCreateParam`). Below 768px it is an accent icon button.
- **Page action.** Every action on one record, or on one part of a destination (a tab, a sub-list, a tender's workspace section), renders in the page's content head row: secondary actions first, then the page's one primary action (`PageHeader primaryAction`).
- **Page head layout.** The first row of the page head holds the back link and subtitle on the left and the page actions on the right, and is at least one button tall. The record meta (reference, status, dates, next action) runs full width below it, so a long meta line never pushes the buttons down and the number of buttons never changes the head's height. The tabs of a record therefore start at the same place on every tab. An inline official deadline always shows its label ("Submission deadline: …").
- The section actions are listed and tested in `src/ui/src/app/sectionActions.test.ts`. The Playwright `layout.spec.ts` checks that the search box and icons keep their position across pages.
